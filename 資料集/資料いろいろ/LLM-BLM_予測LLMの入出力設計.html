予測 LLM の入出力設計

各銘柄の翌月のリターンを予測させる LLM（gpt-4o-mini）に、何を渡して何を受け取るかの設計です。済 は実装済み、予定 はこれから作るもの、未決定 は決めていないものを表します。

1全体の流れ

判断日（各月の最後の取引日）ごとに、その日の S&P500 の構成銘柄すべてについて、次の流れを1回ずつ行います。

今の実装（実行番号 1）は、入力が「社名・業種」と「1か月分の日次リターン」だけです。この設計は、入力の部分を置き換えるものです。出力の形と、Black-Litterman へのつなぎ方は変えません。

2入力

入力を6つのまとまりに分けます。まとまりごとに入れる・入れないを切り替えられるようにし、どれが効いたかを後で測ります（7章）。

C ファンダメンタルズ割安さ、成長、収益性、負債銘柄 × 月（決算のたびに変わる）済（計算済み。プロンプトへの組み込みは予定）

数字の渡し方

セクター内の順位を添える

「PER 32」だけでは高いか安いか判断しにくいので、同じセクターの銘柄の中での位置（0〜100 の百分位）を付けます。対象は、まとまり B と C の銘柄ごとの数字です。

単位をプロンプトに書く

リターンは小数（0.05 ＝ +5%）、VIX と金利は % と、単位をラベルに書きます。今の実装で桁の取り違えが 0 件だった方法を続けます。

欠けている数字は「n/a」

上場して間もない銘柄、赤字で PER が出ない銘柄、業種の性質でその指標が誤解を招く銘柄（銀行の負債、REIT の PER など）は、数字を作らず「n/a」と渡します。0 で埋めると、LLM が本当の 0 と区別できません。

桁数をそろえる

小数は有効数字3桁程度に丸めます。桁が多いと入力が長くなるだけで、情報は増えません。

3未来の情報を使わない決まり

どのまとまりも、判断日より後にわかった情報を入れません。まとまりごとの決まりは次のとおりです。

まとまり使ってよい範囲確かめ方
A 基本情報判断日に指数に在籍していた銘柄だけindex_membership の在籍期間
B 値動き判断日までの株価prices.date ≤ 判断日
C ファンダ判断日までに提出された四半期だけfundamentals_quarterly.filed_date ≤ 判断日
D セクター判断日までのETFの株価と、提出済みの決算sector_metrics.as_of_date ＝ 判断日
E 市場判断日の終値prices.date ＝ 判断日
F レポート判断日までに公表されたレポートのうち、最新の1本reports.published_date ≤ 判断日
モデルの知識知識が 2023年10月までの gpt-4o-mini を使い、評価は 2024年4月からllm_runs.model_version
  • セクターの分類は今の分類です。銘柄のセクターは Wikipedia の最新（または指数を外れる直前）の分類で、過去の時点の分類ではありません。期間中の分類変更は少ないので、影響は小さいと見ています。
  • レポートの公表日は PDF の作成日です。各号は表紙の月の前月下旬に作られているので、N月号を N月の予測に使えます（例：2024年4月号の作成日は 2024-03-27、判断日は 2024-03-28）。

4プロンプトの形

まとまりごとに見出しを付けて並べます。使わないまとまりは、見出しごと省きます。

システムプロンプト（案）

You are a financial analyst. Using only the information given below, predict the average daily return of the stock over the next month.
Every return is a decimal fraction, not a percent: 0.01 means +1%.
Percentile = position among the stocks of the same sector (0 = lowest, 100 = highest).
"n/a" means the value is not available.
Answer the expected average daily return as a decimal fraction (answer 0.001 for +0.1% per day, never 0.1).

入力の長さは、1銘柄あたり約600トークンの見込みです。今の実装（約250トークン）の2倍強で、30個の回答は入力を1回送るだけで受け取れるので、費用への影響は小さいです。

5出力

出力の形は今の実装のままです。

項目内容状態
回答の形JSON で {"expected_return": 数値}。形は API の機能で固定する済
回答の意味翌月の日次の平均リターン（小数）済
回答の数1銘柄・1か月につき30個。1回のリクエストでまとめて受け取る（n=30）済
ばらつきtemperature=1.0。0 にすると30個が同じ答えになり、分散が出ない済
読み取れなかった回答NULL として保存し、平均と分散の計算から外す済

保存先

テーブル・ビュー1行の単位入るもの
llm_runs実行1回モデル、プロンプト、回答の数、temperature、メモ
llm_views実行 × 判断日 × 銘柄 × 回答番号30個の回答そのもの
llm_view_stats（ビュー）実行 × 判断日 × 銘柄回答の平均（Black-Litterman の Q）と分散（Ω）

理由の文章は出させない

回答に「理由」の欄を足すと、30個すべてに文章が付き、出力の費用が数十倍になります。理由を見たいときは、数銘柄だけを別に聞く形にします。

6DB への追加

追加するもの形目的状態
テーブル stock_metrics(as_of_date, symbol, metric, value)。sector_metrics の銘柄版まとまり B・C の数字を保存する。統計モデルの変数としても同じ値を使う済
ビュー stock_metric_scores上の値に、セクター内の百分位を付けるプロンプトに渡す順位済
llm_runs に列を追加inputs（使ったまとまりの一覧を JSON で。例：["A","B","C"]）どの入力で実行したかを残す予定
llm_runs に列を追加user_prompt_template（ユーザープロンプトの型）今はシステムプロンプトしか保存していない予定

LLM に渡した数字と、比較用の統計モデルに入れる数字を、同じテーブルから取るのが要点です。入力が同じでないと、LLM と統計モデルの差が「モデルの差」なのか「入力の差」なのか分けられません。

7実行の条件

まとまりを1つずつ足して実行し、どれが効いたかを測ります。

実行入力確かめること状態
1A ＋ 1か月分の日次リターン既存手法の再現済
2A ＋ B日次リターンの列を要約に置き換えると、なぞりが減るか予定
3A ＋ B ＋ Cファンダを足した効果予定
4A ＋ B ＋ C ＋ D ＋ Eセクターと市場を足した効果予定
5A 〜 F のすべてレポートの文章を足した効果（LLM にしかできない部分）予定
  • 費用：実行 1 は全期間（30か月 × 約490銘柄 × 30回答）で約 1.75 ドルでした。入力が2倍強になっても、1回 3〜4 ドル、4回で 15 ドル程度の見込みです。
  • 比べる相手：同じ B〜E の数字を入れた統計モデル（ロジスティック回帰）。実行 4 と統計モデルの差が「数字の読み方の差」、実行 5 と実行 4 の差が「文章を読んだ効果」です。
  • 見る指標：予想と翌月の実際のリターンの順位相関、予想と入力の相関（なぞりの度合い）、30個の回答のばらつきと実際の外れ方の関係。

8未決定の点

点選択肢今の考え
レポートの文章は全銘柄で同じそのまま全銘柄に渡す ／ セクターの予測にだけ使うまず全銘柄に渡して実行 5 で効果を見る。効かなければセクター予測に回す
1か月のリターンを入れるか入れる ／ 外す入れる。短期の反転は知られた傾向で、1個の数字ならなぞりの問題は小さい
百分位の母集団セクター内 ／ 指数全体セクター内。業種で水準が違う指標（PER、負債）が多いため
業種によって意味が変わるファンダほかと同じ項目 ／ 項目を変える決定：業種の性質で誤解を招く指標は作らない（n/a）。銀行・証券などは純利益率と負債の重さ、REIT と複合持株会社は PER・純利益の前年同期比・純利益率・ROE
